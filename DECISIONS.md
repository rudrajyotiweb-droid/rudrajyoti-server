# Decisions (backend phase)

| # | Decision | Why |
|---|---|---|
| 1 | **Express 5 + MongoDB/Mongoose** instead of the BRD's Next.js API + PostgreSQL/Prisma. | Client asked for Express and MongoDB (Atlas cluster provided). Express 5 forwards async errors to the error handler, so no try/catch wrappers are needed in routes. |
| 2 | **Paytm** instead of Razorpay; **Message Central (VerifyNow)** for OTP instead of MSG91. | Client's choice. Both sit behind small services (`services/paytm.js`, `services/messageCentral.js`) so another provider can be added without touching routes. |
| 3 | Images and videos are stored **in MongoDB GridFS** and served at `/media/<key>`. The seed uploads every file from `client-site/public/assets/images` and `/brand`. | Client wanted the site images "in the database". GridFS needs no extra service. Move to a CDN/object store later if video volume grows (only `services/media.js` changes). |
| 4 | Money is stored as **whole rupees** (integers), not paise. | Every price in the catalog is a whole rupee amount and the UI formats rupees; it avoids conversions in two frontends. Paytm gets `amount.toFixed(2)`. |
| 5 | Prices are **GST-inclusive**; GST is back-calculated for display and invoices. | Matches the existing UI ("incl. all taxes") and Indian retail practice. |
| 6 | Payment status is decided only by Paytm's **order-status API**, never by what the browser or the callback form says; the amount is re-checked. | Callbacks and client events can be forged or lost. |
| 7 | Store stock is **reserved when the order is created** (atomic conditional decrement) and released if payment fails or expires (30 min mock / 3 h Paytm). | Prevents overselling the last item to two customers. Chadhava item limits are checked at checkout and counted on payment (small overshoot possible at the limit edge). |
| 8 | Abandoned checkouts stay as `Pending Payment` / `Payment Failed` and are hidden from devotees' lists and admin lists by default (`includePending=true` shows them). A failed payment can be retried on the same booking. | No duplicate bookings when a devotee retries. |
| 9 | Devotee auth: short-lived JWT access token + **rotating refresh token** stored hashed in `sessions`; reuse of an old refresh token signs the user out everywhere. Tokens are sent as Bearer headers (not cookies). | Frontends live on different domains (Netlify), where third-party cookies are unreliable. |
| 10 | Admin auth: email + password (bcrypt, lockout) + **optional TOTP 2FA** that each admin turns on in Settings → My account. | BRD asks for mandatory TOTP; it is optional at first so the client can sign in before setting up an authenticator app. Make it mandatory with a one-line check in `routes/admin/auth.js` once all staff have enrolled. |
| 11 | Development fallbacks: `OTP_PROVIDER=console` (fixed OTP) and `PAYMENT_PROVIDER=mock` (instant test payments). The API **refuses to start** with either in production. | The whole flow can be tested before the client has Message Central / Paytm keys. |
| 12 | Notifications are **in-app** (stored per user, shown in Account → Notifications) for every booking/order status change, admin reply and campaign. WhatsApp/SMS/push adapters plug into `services/notify.js`. | No WhatsApp Business API account yet. The admin "Push notifications" screen sends in-app campaigns. |
| 13 | Shipping is manual (courier + AWB entered in admin) — no Shiprocket integration yet. | No Shiprocket account. The AWB is required before an order can be marked shipped. |
| 14 | Pujas move to `Closed` automatically when their cutoff passes (background job). | BRD §13.1. Seeded demo dates are relative to the seed day, so re-run `pnpm seed:fresh` or edit dates in the admin when demo pujas close. |
| 15 | Demo reviews are seeded only outside production, flagged `isDemo`, and the public API hides them when `NODE_ENV=production`. | BRD §6.13 — no fake reviews in production. |
| 17 | One admin account. The API keeps role fields and `/admin/staff` routes internally (super-admin only), but the admin panel exposes no staff/roles UI. | Client removed staff & roles on 2026-10-16: only one admin plus customers. |
| 18 | Site settings also hold `pageImages` (header images of fixed pages) and `howItWorks` steps; defaults point at the seeded `/media` files and are merged in automatically, so existing databases get them without reseeding. | Lets the admin change every image the design shows. |
| 16 | Analytics for the Reports funnel and traffic sources are anonymous daily counters (`metrics` collection), not per-user tracking. | Enough for the admin report without storing personal data. |
